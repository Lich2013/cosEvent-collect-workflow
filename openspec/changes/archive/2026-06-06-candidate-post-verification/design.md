## Context

当前系统的 Coser 候选人验证流程由 `DiscoveryService.verify_pending_candidates` 实现。其流程是：从 `coser_candidates` 表中过滤未验证候选人，若有 pre-bound UID，则通过 B 站主页解析拦截 `api.bilibili.com/x/space/wbi/acc/info` 接口，读取其个人空间简介（Bio）并进行二次元关键词匹配核验。

然而，仅依赖空间简介（Bio）关键词匹配存在以下弊端：
1. 大量活跃的 Coser 并没有在 B 站或微博简介中填写包含 "cos", "coser", "cosplay" 等关键词，导致这部分高素质 Coser 候选人被误杀忽略。
2. 无法对候选人近期发表的动态进行活性核验。有些候选人虽然简介符合，但账号已长期不活跃。

为了提高验证召回率，我们决定引入候选人博文内容 LLM 智能体文本分类核验。通过在验证阶段轻量级爬取候选人最新的 3~5 条博文，使用 LLM 判别其是否发布过 Cosplay/漫展日程相关内容。

## Goals / Non-Goals

**Goals:**
- 在数据库中新增 `candidate_raw_posts` 物理表，用于存放待验证候选人的博文，与正式 Coser 博文解耦，秉承物理隔离原则。
- 在 `coser_candidates` 中新增 `verify_reason` 属性，用于持久化记录大模型的核验判定理由。
- 升级爬虫调度，支持在验证候选人时以低优先级抓取候选人的最新 3-5 条博文文字。
- 构建 `CandidateVerifyAgent` 纯文本核验智能体，利用 LLM 进行分类判定并给出理由。
- 在终端 CLI 表格中优雅展现候选人的核验详情（是否已核验、LLM 核验理由）。

**Non-Goals:**
- 不引入多模态（图片）分析评分过滤，只通过博文的文本内容进行分类。
- 不在此阶段提取候选人博文的具体漫展行程（不存入正式活动表），此阶段仅做 Coser 身份核验。
- 不对候选人的博文进行长期、全量的跟踪抓取。一旦核验完毕（无论成功与否），该候选人的博文爬取即告结束。

## Decisions

### 1. 博文表设计：物理隔离 vs 统一表
- **方案 A**: 在 `raw_posts` 中使 `coser_id` 允许为空并增加 `candidate_id` 字段，合二为一。
- **方案 B**: 新建 `candidate_raw_posts` 表。
- **决定**: 采用 **方案 B**。候选人的数据具有临时性和高噪声性，与正式追踪的 `raw_posts` 分离，能最大程度保证生产表的数据清洁度与索引性能，且完全避免了修改已有 `raw_posts` 外键关联和相关 `JOIN` 逻辑带来的系统级退化风险。

### 2. 博文分析方案：文本分析 vs 多模态图片分析
- **方案 A**: 下载图片并调用多模态模型进行美学评分与妆造判定。
- **方案 B**: 仅抓取博文的文本内容（如“今天CP30返图...”、“下周六去罗森一日店长...”），使用轻量级文本 LLM 进行相关性分类。
- **决定**: 采用 **方案 B**。虽然多模态更直观，但涉及图片下载、反热链防爬风控、高昂的 API Token 消耗以及复杂的提示词对齐，开发难度大且不稳定。文本分析在成本、抗风控和开发速度上具有压倒性优势，足以覆盖 90% 以上的活跃 Coser 核验需求。

### 3. 核验判定逻辑与生命周期
- **逻辑**: 对每个需要核验的候选人，首先进行 Bio 核验。若 Bio 已经包含明显的二次元关键词，或者博文分析判定为 Coser，则 `is_verified` 置为 `1`。
- **状态回写**: 
  - `is_verified = 1`: 审核通过，并在 `verify_reason` 中记录 LLM 的依据或 "Bio 关键词匹配成功"。
  - `status = 'ignored'`: 核验失败，将其归档，下轮调度不再重试。

## Risks / Trade-offs

- **[Risk]** 批量爬取候选人博文可能会快速消耗 B站/微博接口的爬虫频控额度，甚至导致 IP 被封。
  - **Mitigation**: 严格限制候选人抓取频率，单次验证批量上限默认不超过 10 个；抓取条数硬限制为 3-5 条；抓取完成且 LLM 分析出结果后，立即将候选人移出验证队列，确保每个候选人只会被爬取一次。
- **[Risk]** LLM 可能会将偶尔转发动漫相关动态的普通用户误判为 Coser（假阳性）。
  - **Mitigation**: 在 `CandidateVerifyAgent` 的 System Prompt 中加入具体的 Few-shot 负例指导，强调必须是“自己扮演角色”、“发布个人返图/场照”或“有出行排班计划”的用户才能判为 `True`。
