## Context

当前系统由 `EventFusionService` 在分析阶段（`analyze`）直接实时更新 `normalized_events` 并建立外键绑定。当发生小众活动合并或常规漫展去重时，系统执行的是破坏性的 `UPDATE` 或 `DELETE` 语句，直接修改了 `cosplay_events` 的外键绑定或删除了 Loser 节点。

这带来两个致命局限：
1. **数据无法无损回溯**：如果分析逻辑或去重边界未来发生调整，我们已无法还原原始爬取的排班，因为日程表中的外键已经原地变动。
2. **SQLite 锁冲突**：多个爬虫-分析器并发写数据库时，原地更新大表极易锁定 `normalized_events`，导致前台读取超时或崩溃。

## Goals / Non-Goals

**Goals:**
- **读写分离与只读日程**：保留 `cosplay_events` 纯净的数据事实，分析器仅做增量只读插入，不作任何物理合并或超级节点改写。
- **冷热数据滑动窗口去重**：仅对 `今日 - 30天` 以内的活跃日程及近期发布的时间未知日程，进行内存级别的融合聚类计算。
- **持久化确定性指纹 ID**：物化表的主键必须基于内容特征生成确定性的哈希指纹，即使多次擦除重建，ID 也绝不抖动，保护前台路由生命周期。
- **批处理解耦重建**：将呈现表的生成时机与分析流程解耦，固定在 `process` 主链任务结束时一次性批重构，规避锁竞争。

**Non-Goals:**
- 不修改 `raw_posts` 与 AI Extractor 提炼打标流程。
- 不引入复杂的分布式 KV 缓存或消息队列，继续保持单机 SQLite 的轻量级与极简性。

## Decisions

### 1. 确定性哈希 ID (Deterministic Hashing) 替代自增主键
- **方案选择**：物化超级节点表 `final_exhibition_view` 的主键 ID 采用 `MD5(city + name_slug + event_type + date_bucket)` 计算出的 32 位十六进制字符串。
- **决策 rationale**：
  - *自增主键（被弃用）*：清空重建时，自增主键每次都会打乱重排，导致前台收藏的链接 `/event/101` 瞬间失效。
  - *确定性 MD5 哈希（本方案）*：无论物化视图重建多少次，相同的城市、同名、同类型、同年份的超级节点所算出的哈希串永远恒定。前台收藏的哈希路由永久有效。

### 2. 活动级冷冻机制 (Exhibition-Level Freezing) 规避边界泄漏
- **方案选择**：将冷热交界线定为 `T_cold = 今天 - 30天`。冷冻判定不以单条排班日期为准，而是根据超级节点的极大值 `end_date` 进行整展冷冻。
- **决策 rationale**：
  - *单条日程冷冻（被弃用）*：如果一个跨窗口的大型漫展（如 04-28 到 05-03）的部分日程落入冷区被冻结，剩余日程在热区会被误判为新漫展，产生物理分裂。
  - *整展级冷冻（本方案）*：只有当该节点下的所有日程都落入冷区时，才整体冻结，完美避免了交界线处的“边界分裂”与“漏合并”漏洞。
- **针对未知时间日程的博文发表期判定**：对于日期为 `"未知"` 的日程，若其原始博文发表日期（`published_at`）早于 30 天之前，在逻辑上视为已举办过的冷数据，进行物理冻结，不再参与热数据物化计算。

### 3. 物化表结构预聚合与呈现分离
- **方案选择**：物理新建三张解耦表：
  1. `cosplay_events` (事实表，只读，记录 raw_event_name、raw_event_place)。
  2. `event_mappings` (中间关系表，记录 raw_event_id 与 normalized_event_id 的哈希绑定)。
  3. `final_exhibition_view` (物化呈现表，只存储确定性哈希主键及预聚合的 Coser 列表、排期极大值)。
- **决策 rationale**：数据以高维预聚合 JSON 列的形式在物化表中进行单行集结，大幅提升前台看板的查询效率，使多表复杂联查降级为 $O(1)$。

### 4. 批重建与异步延迟物化时机
- **方案选择**：在 `src/main.py` 的 `process` 主命令以及 CLI 工具最末尾，一次性调用物理物化重建 `MaterializeService.rebuild_view()`。
- **决策 rationale**：避免了分析阶段（Analyze Phase）每一条微博入库都触发物理物化，彻底释放了高频分析下的 SQLite 并发锁竞争，读写性能大幅提升。

## Risks / Trade-offs

- **[Risk 1] 内存中全量热聚类的性能抖动**
  - *Mitigation*：热活跃日程及 30 天内未知日程在常规状态下数量恒定（通常小于 500 条），在内存中运行 $\pm 7$ 天窗口与 similarity 矩阵计算只需毫秒级，性能开销可忽略不计。
- **[Risk 2] 人工手动纠偏配置在重建时被覆盖**
  - *Mitigation*：在数据库中创建 `manual_overrides` 关系表，存储用户手动对齐的 `(raw_event_id, target_normalized_id)`。在重建算法运行结束后，二次读取该表强行覆盖映射，完美保留人工纠偏。
