## ADDED Requirements

### Requirement: 读写分离与只读日程事实表物理归档
系统在进行小众活动或常规漫展融合去重时，**严禁且 SHALL NOT** 直接物理更新或删除 `cosplay_events` 日程日程记录中的原始字段（如 `event_name`, `event_date`）。所有由 Extractor 智能体提炼出的大模型原始事实数据，必须以**只读事实表（Read-Only Fact Table）**的形式永久物理留存，不对历史排班进行破坏性覆盖。

#### Scenario: 成功追加分析新排班而不修改任何既存日程记录
- **WHEN** 运行 analyze 任务，分析出 Coser A 新增了名为 “Nikke罗森一日店长” 的排班日程
- **THEN** 系统在 `cosplay_events` 事实表中追加写入一行新记录，而库中既有的其他 Coser 原始排班行、原始字样均完好无损，没有发生原地 UPDATE 物理覆盖

### Requirement: 滑动冷热区间划分与未知时间日程逻辑冷冻
系统在物化呈现阶段，必须且 SHALL 执行冷热数据滑动窗口分区计算，仅对活跃的热日程进行增量物化聚类以保障性能：
1. 热活跃窗口阈值：设定为 `T_cold = 今天 - 30天`。
2. 历史冷整展冻结：对于有明确日期的超级节点，只有当该节点下的最大结束时间 $\max(\text{event\_date}) < T_{cold}$ 时，才将其及级联日程在物化视图表中标记为冻结（`is_frozen = 1`），防止“边界分裂”与“漏合并”；
3. 未知时间逻辑冷冻：对于 `"未知"` 日期的日程，若其关联博文的发布时间 `raw_posts.published_at` 早于 30 天之前，系统必须将其标记为冷数据（`is_frozen = 1`）进行归档冷冻，不再参与活跃区物化计算。

#### Scenario: 活跃店长日程正常参与热去重聚类，而古老未知日程被安全冻结
- **WHEN** 重建物化呈现视图时，检测到 10 天前的活跃日程“Nikke罗森一日店长”（热日程）与 90 天前发布且至今未纠偏的未知时间“店长”（冷日程）
- **THEN** 活跃店长日程正常进入热活跃聚类算法并重新秒配归一化，而古老未知日程被物理冻结，跳过相似度计算与 AI 裁判，直接归档至历史展示分区

### Requirement: 确定性指纹哈希 ID 与物化展示表
系统必须在物化呈现表 `final_exhibition_view` 中为每个归一化的超级节点生成确定性的主键 ID，生成算法必须且 SHALL 强制使用内容哈希公式 `MD5(city + name_slug + event_type + date_bucket)`，物理规避清空重建导致的主键自增抖动，保障前台 URL 路由生命周期的绝对稳定性。

#### Scenario: 物化视图多次擦除重建后超级节点 ID 保持绝对恒定
- **WHEN** 在同一份包含“上海CP30”的测试数据集上连续执行 5 次物化表擦除与重建任务
- **THEN** “上海CP30”在 `final_exhibition_view` 表中的主键 ID 在 5 次运行中均保持为唯一的 MD5 确定性哈希值，未发生任何数字自增抖动

### Requirement: 批重建时机控制与原子事务强锁
系统必须将物化重建时机与常规抓取分析流程完全解耦，**严禁且 SHALL NOT** 在 analyze 增量入库时高频写入物化表。系统必须且 SHALL 在 `process` 主命令行任务链完全结束的最末尾、或用户手动调用时，在单一 `BEGIN IMMEDIATE` SQLite 原子写锁事务中，一次性快速执行全量活跃物化重建。

#### Scenario: 在 process 结束时触发单次无锁竞争的物化重建
- **WHEN** 命令行调用 `uv run python src/main.py process` 执行完整流
- **THEN** 前期爬行和 AI 提炼对物化表零写操作，在所有博文分析完毕后，系统以原子事务强锁一次性刷新物化表热区数据并成功提交，前台读取未发生任何 lock 竞争报错
