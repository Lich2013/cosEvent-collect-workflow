## Context

当前系统支持多平台（Weibo, Bilibili, XHS）日程提取和以漫展为中心的时空聚类。但是在数据落地与展现层，存在以下局限：
1. `cosplay_events` 仅支持对当前分析博文的历史版本进行软取消。对于 Coser 同平台多次发帖或跨平台多重发布同一日程，系统会录入完全重复的日程，导致数据库产生冗余。
2. 同一同人祭或展会在不同 Coser 那里有极高程度的简称别名差异（如 "上海bw" vs "bilibiliworld"）， difflib 相似度极低（<0.5），由于超出了金牌裁判拦截范围，直接产生了超级漫展节点的分裂和碎片化。
3. 部分高频热门活动在 Coser 正文中由于缺省默认被大模型标记为 `'未知'`，无法展现完整的排期脉络，而实际上该超级节点的举办包络时间已被其他 Coser 的日程标定。

## Goals / Non-Goals

**Goals:**
- **跨平台/多发帖全局 In-place 去重**：实现同一个 Coser 对同一个超级漫展的相同日期（或未知日期）日程的合并去重。当新日程到达时，进行 In-place 覆盖合并更新（合并描述与链接），零冗余。
- **别名相似度预处理与时空裁判扩容**：在 `EventFusionService` 前置注入常见缩写映射字典（如 "bw" -> "bilibiliworld", "cp" -> "comicup"）；同时，对于“同城同档期且重叠在 3 天内”的模糊节点，扩容 LLM 裁判的拦截和判定范围。
- **只读看板时间继承机制**：在日历看板、日程看板与数据导出层，对 `'未知'` 日期日程实时、自动地继承其超级漫展节点的 start/end date 范围，并显示 `(推算自超级节点)`。

**Non-Goals:**
- 不变更 `cosplay_events` 与 `normalized_events` 表的基础 Schema，不改变物理外键关系。
- 展现层的时间继承采取只读计算（方案 A），绝不在数据库物理表中反向强制覆写 `'未知'` 原始字段，完全保持数据的高保真可追溯性。

## Decisions

### 决策 1：在 `EventRepository.save_extracted_events_transactional` 中引入全局 Coser 日程 In-place 智能 Upsert
- **设计**：在 IMMEDIATE 排他事务锁内，遍历每个提炼出的新活动事件。
  - 检查该 Coser 是否已在 `cosplay_events` 表中存在关联了**相同 `normalized_event_id`**，且**日期一致或相容**的未来日程记录（未取消）。
  - 如果不存在：正常执行新日程插入。
  - 如果已存在：
    - **In-place 合并**：不进行新行插入，而是更新该已存行的 `event_description`（将新旧描述中更丰富者保留或合并，如 `old_desc + " | " + new_desc`），更新 `raw_post_id`、`source_url` 和 `confidence` 到最新，避免数据库产生冗余记录。
- **理由**：能够以极简、最内聚的数据流实现单人跨平台日程的 100% 融合，并在物理层完全消除了冗余重复日程。

### 决策 2：缩写清洗替换与自适应裁判扩容
- **设计**：
  1. 在 `EventFusionService._clean_name` 中增加 ACG 常用简称模糊转换：
     ```python
     s = s.replace("bw", "bilibiliworld").replace("cp", "comicup")
     ```
  2. 扩大同城同档期的时空裁判介入范围：若既存超级漫展与新日程同城，且时间在 $\le 3$ 天的重叠窗口内，即使 difflib 相似度极低（将下限从 $0.5$ 放宽至 $0.2$），也强制拉起一次 LLM 裁判判定。
- **理由**：通过对齐 `"bw"` 和 `"cp"`，能直接让 SequenceMatcher 匹配成功，直接合并；而对于拼写更随意的 `"bili world" vs "上海bw2026"`，扩容后的 LLM 裁判可以通过一次性的 Token 裁决写入 `event_aliases` 别名表，后续直接旁路 0% 消耗，兼顾了高精准与低成本。

### 决策 3：只读看板层（View-level）对 `'未知'` 日期日程自动继承超级节点包络时间
- **设计**：重构 `QueryService` 的查询 SQL 和 `TerminalRenderer` / `ExportService` 展现逻辑：
  - 当读取到 Coser 日程的 `event_date` 为 `'未知'` 时，系统获取其绑定的 `normalized_events` 超级漫展的 `start_date` 和 `end_date`。
  - 若超级节点具有有效的起止日期（不为 `'未知'`），系统在控制台和导出时，自动格式化并展现其为：`f"{start_date} 至 {end_date} (推算自超级节点)"`。
- **理由**：保持物理表的高保真性（尊重原始发帖没写事实），通过 View 展现层实现智能继承，免除了数据库回写造成的物理数据踩踏和复杂的刷表磁盘 I/O。

## Risks / Trade-offs

- **[Risk] 不同平台的日程描述合并时产生语义冲突或超长字符串**
  - **Mitigation**: 在 In-place 合并时，如果新旧描述有相似的词根，我们可以直接保留最长最详细的那一个；如果描述完全不同，则以 `" | "` 作为连接符拼接（例如：“第一天出黄泉 | A15摊位签售”），并在拼接前对内容进行去重清洗，保障内容的可读性。
- **[Risk] 别名裁判介入范围下限放宽至 0.2 是否会带来多余的 LLM 判定开销？**
  - **Mitigation**: 我们仅在 **“同城”** 且 **“时间窗高度重叠（<= 3天或包含未知）”** 的核心候选节点下才放开下限，对于非同城或大跨度的日程完全过滤。加之 `event_aliases` 的别名缓存极度敏捷，相同的简称一旦判定一次就永久缓存，因此额外 Token 开销微乎其微。
