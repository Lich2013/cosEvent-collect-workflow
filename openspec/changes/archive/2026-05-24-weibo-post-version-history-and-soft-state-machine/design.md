## Context

系统目前对于置顶微博的长效行程汇总采用“首发发布时间锁死”和“物理清除未来日程”策略。
当 Coser 跨越年度对置顶博文（首发于 2024 年，编辑于 2025 年）进行修改更新时，大模型在接收到 2024 年的 `published_at` 时会错误地将 2025 年新行程（如“10.6”）计算回 2024 年，因年份在系统参考时间（2026 年）之前而全数被系统判定过期过滤，导致分析失败。
同时，利用 `DELETE` 物理清除被取消的行程非常危险，且抹杀了历史变更的线索。因此需要重构为“微博只增不改版本化存储”与“日程软状态机管理”方案。

## Goals / Non-Goals

**Goals:**
- 在 `weibo_scraper.py` 中捕获 `edit_count > 0` 的编辑博文，动态将其 `post_id` 转换为 `post_id#v{edit_count}`，并将其 `published_at` 重锚（Re-anchor）为当前北京抓取时间，保证版本独立性与大模型语义相对时间年份对齐。
- 在 `db_models.py` 的建表与初始化阶段，为 `cosplay_events` 在线追加 `'status'` 状态属性列（文本型，默认 `'未开始'`），淘汰高危硬删除。
- 在 `db_service.py` 保存活动数据时，锁定当前逻辑博文的所有历史版本（首发及其他 `#v` 编辑版本），并对其未来的未办行程执行精细化软清理（`UPDATE status = '已取消'`），对历史已办日程执行冷冻固化保护。
- 在 CSV 导出服务和有效日程获取接口中，自动在 SQL 查询阶段过滤屏蔽 `'已取消'` 状态的失效行程。
- 更新测试套件 `tests/test_cosevent.py`，实现版本控制、时间重锚与日程状态流转的单元测试覆盖。

**Non-Goals:**
- 不改变大模型智能体与裁判的核心 Pydantic 返回强契约（`CosEvent` 数据结构维持纯净，`status` 属性仅在本地数据库业务层与事务插入阶段由 `DBService` 自动维护注入，LLM 无需感知该属性）。
- 不破坏 SQLite 原生的外键关联级联规则，保留 `ON DELETE CASCADE` 约束。

## Decisions

### 决定 1：在爬取阶段实施后缀版本化与发布时间重锚
- **决策内容**：在 `weibo_scraper.py` 数据组装逻辑中判定 `edit_count > 0`。一旦有编辑，`post_id = f"{post_id}#v{edit_count}"`，且 `published_at = datetime.datetime.now(beijing_tz).strftime("%Y-%m-%d %H:%M:%S")`。
- **原由与收益**：
  - **完全免除 Schema 变更**：新版本后缀是唯一的，在 `raw_posts` 中会被自然判定为新插入行，从而在不修改数据库 `raw_posts` 任何字段的前提下完美实现了版本快照的追加存档（Append-only）。
  - **解除时间幽灵限制**：重锚时间到当前抓取年份，使 LLM 能以当前最新现实时间推导相对日期，彻底解决了置顶微博更新后提取数归零的严重 Bug。

### 决定 2：引入软状态机管理，实施精细化的跨版本级联软取消
- **决策内容**：升级 `cosplay_events` 追加 `'status'` 字段（包含 `'未开始'`, `'已结束'`, `'已取消'`），并在写入新版行程时，事务中对该逻辑 ID 既往全部历史版本的未来有效行程进行软注销：
  ```sql
  UPDATE cosplay_events 
  SET status = '已取消' 
  WHERE raw_post_id IN (该博文所有版本 ID) AND event_date >= ? AND status = '未开始';
  ```
- **原由与收益**：
  - **杜绝高危删除**：彻底杜绝物理 `DELETE` 的高危行为，在工业上保证了数据资产的安全性与完整性。
  - **数据资产化留痕**：保留了 Coser 从“未开始”到“已取消”的状态转移记录，这本身为二次元情报数据分析提供了最完整的一手行程变动和出装变更数据，极大提升了行程表的历史追溯审计价值。

## Risks / Trade-offs

- **[风险 1] 数据库追加列迁移可能因表锁死或重复执行报错**  
  * **缓解措施**：在 `db_models.py` 的迁移检查中，使用 SQLite 内置的 `PRAGMA table_info(cosplay_events)` 精准嗅探是否存在 `'status'` 列，仅在其确实不存在时才执行 `ALTER TABLE` 操作，避开任何不必要的错误产生。
- **[风险 2] 大模型重新提取后产生老数据堆积**  
  * **缓解措施**：由于在保存活动事务中强力实行了基于 `event_date >= 当前日期` 的未来日程 `'已取消'` 精准软状态转化，同时在 CSV 导出查询中排除了 `'已取消'` 状态，因版本交替引起的脏数据会被物理隔离得一干二净。
