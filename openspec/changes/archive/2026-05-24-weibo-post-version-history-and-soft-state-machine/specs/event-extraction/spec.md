## ADDED Requirements

### Requirement: 日程软状态机管理与跨版本级联状态转移规范
为了在彻底淘汰高危物理删除（Hard Delete）动作的前提下实现排班表变更的无损对齐，并保持极高的行程历史追溯审计能力，系统在写入提炼日程时，**必须且 SHALL** 建立并执行日程“软状态机”（Soft State Machine）管理规范：
1. **状态字段与在线升级**：本地数据库表 `cosplay_events` **必须且 SHALL** 维护状态列 `status`（TEXT 类型，默认值 `'未开始'`），用于追踪日程的生命周期：
   - `'未开始'`：未来有效即将举办的日程。
   - `'已结束'`：已在时间轴上流逝完成的历史日程。
   - `'已取消'`：软删除废弃日程（由 Coser 后续编辑动作所废弃撤销的日程）。
   系统必须在初始化阶段具备热迁移能力，检测并在列缺失时自动安全追加 `status` 字段列。
2. **跨版本精细化级联软状态转移**：在保存最新版本博文（如 `post_id#v2`）提炼的新活动记录时，系统**必须且 SHALL** 在同一个原子性数据库事务中执行以下比对和软清理：
   - 提取逻辑主博文 ID（剥离 `#v` 后缀），检索所有属于该博文各个旧历史版本的已存活动记录；
   - 凡是历史活动 `status = '未开始'` 且其举办时间早于当前抓取日期 (`event_date < 当前参考日期`) 的，一律视为“已发生的历史日程”并予以**冷冻保护**，禁止做任何状态干涉以保留其真实历史足迹；
   - 凡是历史活动 `status = '未开始'` 且其举办时间大于等于当前抓取日期 (`event_date >= 当前参考日期`) 的，一律视为失效的“多余未来日程”，系统**必须且 SHALL** 执行 `UPDATE` 更新其 `status = '已取消'`（软删除），将其置为注销状态以彻底避免重复。
3. **数据报表与导出状态过滤**：在执行 CSV 表单数据导出或任何有效日程的前端检索时，系统**必须且 SHALL** 在 SQL 查询层过滤剔除状态为 `'已取消'` 的脏数据，仅展现 `'未开始'` 与 `'已结束'` 的行程。

#### Scenario: 成功流转历史版本未来日程为已取消状态并实现冷冻保护
- **WHEN** 触发保存最新 `post_id#v2` 版本提取日程，且此前数据库中存在历史版本对应的未来日程与历史日程时
- **THEN** 历史版本中的未来行程 `status` 被成功更新转移为 `'已取消'`，历史已办行程状态保持不变，导出 CSV 时已取消的行程被自动过滤排除。
