## MODIFIED Requirements

### Requirement: 智能二次元小众日程识别、提炼与值域防御
系统必须能够智能识别、分流预检并提炼二次元小众线下日程（如一日店长、到店特邀模特、摄影会、快闪/签售等），并在物理存储与模型校验上进行严格的类型打标与值域双重防御。
1. **预检分流（Triage）放行**：
   - 预检分流智能体（Triage Agent）在首轮处理博文时，若识别出未来包含“一日店长”、“受邀模特”、“摄影会”、“快闪/签售”等小众二次元线下活动日程，系统 MUST 判定首轮预检分流契约 `has_event` 为 `True`，以确保小众日程不被漏报误杀。
2. **结构化提取（Extractor）与物理打标**：
   - 提炼智能体（Extractor Agent）返回的 Pydantic 强契约数据结构 `CosEvent` 中，必须新增 `event_type` 字段，且其提取的值必须为 `('漫展', '一日店长', '摄影会', '受邀模特', '快闪/签售')` 之一。
   - 严禁在 `CosEvent` 声明中包含 `coser_name` 字段，以防产生 LLM 幻觉。
3. **应用与物理表双重防御**：
   - 在将提炼出的活动日程持久化入库或更新时，系统必须且 SHALL 在进入事务前通过嵌套辅助验证函数（`validate_type`）执行值域断言。
   - 数据库物理建表或热升级中，`cosplay_events` 表必须物理新增 `event_type` 字段（`TEXT` 类型），包含 `DEFAULT '漫展'`，并设置相应的 `CHECK (event_type IN ('漫展', '一日店长', '摄影会', '受邀模特', '快闪/签售'))` 约束，实现数据库底层的值域硬核防线。对存量老数据，必须向后兼容默认补全为 `'漫展'`。
4. **旁路与时空融合引擎智能对齐**：
   - 物理入库小众二次元日程时，系统 **严禁且 SHALL NOT** 采用无差别的 100% 旁路时空融合规则。
   - 系统必须且 SHALL 根据小众活动名称进行智能闸门特征拦截：仅当小众日程的清洗后名称命中泛指黑名单、或者长度小于等于 3 且不包含任何主要展览地级市名时，才执行 100% 旁路以防止泛称强坍塌；对于具体的、具有特定命名的小众日程（如“明日方舟Only”、“罗森一日店长”、“罗森店长”），必须通过 O(1) 秒配及常规时空匹配进行物理合并。

#### Scenario: 成功预检并提炼罗森一日店长小众日程
- **WHEN** 解析博文内容“11月8日沪闵路9505号～ Nikke罗森一日店长，大家到时候见哦！”且该博文发表时间为 `2026-11-01`
- **THEN** 系统判定 `has_event` 为 `True`，Extractor 提取出的 `event_type` 值为 "一日店长"，城市提取为 "上海"，日期提取为 "2026-11-08"，且在保存数据库前成功通过 `validate_type` 断言校验，并进入融合引擎匹配

## ADDED Requirements

### Requirement: 专有名词小众日程智能闸门化融合
系统在处理二次元小众活动（`event_type != "漫展"`）时，必须执行智能旁路闸门（Gated Bypass）机制：
1. 泛指名称黑名单：系统必须预设包含“签售”、“一日店长”、“店长”、“摄影会”、“受邀模特”、“快闪”、“签售会”等极简名词的黑名单。
2. 拦截与放行决策：当且仅当活动名称清洗后（name_slug）满足条件：`(name_slug in BYPASS_GENERIC_NAMES) 或 (len(name_slug) <= 3 且无地级市名)` 时，系统 SHALL 判定为极简活动并 100% 旁路时空融合独立建档；否则，系统必须将其放行进入 O(1) 秒配与常规时空融合通道。

#### Scenario: 专有名词店长活动被放行并成功融合
- **WHEN** 输入小众一日店长活动为“Nikke罗森一日店长”，城市为“上海”，日期为“2026-11-08”，库中已存在相同指纹的超级节点
- **THEN** 系统判定该名称不属于极简泛称，放行通过旁路闸门，并在 O(1) 快速通道中成功秒配并合并，返回该超级节点 ID

#### Scenario: 边界四字店长活动被成功放行融合
- **WHEN** 输入小众日程名称为“罗森店长”（长度为 4 且不在泛指黑名单内），城市为“上海”，日期为“2026-11-08”，库中已存在该城市同天同名超级节点
- **THEN** 系统判定该活动长度大于 3 且不命中黑名单，放行通过旁路闸门，并在常规时空融合中成功秒配并合并，返回该超级节点 ID

#### Scenario: 极简一日店长活动被安全旁路独立建档
- **WHEN** 输入小众日程名称仅为“一日店长”，城市为“上海”，日期为“2026-11-08”
- **THEN** 系统判定其命中了泛指黑名单，触发 100% 旁路，不运行融合裁判，直接安全生成独立的全新超级节点

### Requirement: 数据库存量超级节点一键式原子事务去重 CLI 指令
系统必须提供命令行去重指令 `deduplicate`（通过 `uv run python src/main.py deduplicate` 执行），以物理修复数据库中历史遗留的分裂超级节点：
1. 规则判定与时间窗口：系统必须在 `[city, name_slug, date_window]` 范围内自动聚合冗余的超级节点。其中时间窗口必须严格使用与 O(1) 通道完全对齐的 **`±7 天`** 保护。选取 ID 最小的作为 Winner 节点，其余作为 Loser 节点。
2. 级联重定向：系统必须且 SHALL 执行数据库级联 `UPDATE`，将所有绑定在 Loser 节点上的 `cosplay_events` 重定向绑定到 Winner 节点。
3. 别名表冲突自愈与审计：对于 Loser 关联的别名，系统尝试更新其 `normalized_event_id`。若触发 UNIQUE 主键冲突，系统必须输出 `[Spatial Rectification Audit]` 警告审计日志（记录 Winner ID、冲突别名与冲突详情），并安全 `DELETE` 冲突的别名行。
4. 节点安全清理：系统必须删除 Loser 节点，且删除语句必须使用 `try-except sqlite3.IntegrityError` 进行防御包裹，防止由于外键约束引发物理崩溃。
5. 事务性原子屏障：上述所有的去重及物理更新操作，必须且 SHALL 包裹在同一个数据库原子 SQL 事务中运行，发生任何错误必须物理 `ROLLBACK`。

#### Scenario: 成功运行一键式去重且不发生别名表死锁崩溃
- **WHEN** 命令行调用 `uv run python src/main.py deduplicate` 运行去重清洗
- **THEN** 系统在同一个原子事务中，将冗余的“石家庄Mars EXPO签售”超级节点在 ±7 天窗口内成功重定向，在 alias 冲突时输出 Audit 日志并合并，安全物理清理 Loser 超级节点，整个事务成功提交且无任何 `sqlite3` 崩溃报错
